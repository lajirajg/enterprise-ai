# Design decisions and provenance

## Confirmed intent

The owner requested end-to-end coverage, visible planned content, a business outcome view, five operating layers and three spines, and low-friction resource capture. Intelligent Core is the technical AI platform view. Data & Digital Core represents digitised business processes, systems and data. Continuous improvement remains Layer 4.

## Reference handling

The supplied architecture image and Modern Operate deck were inspected as private reference material. Only the high-level structure is retained here. The public capability definitions and examples were written afresh. No source attachment, extracted text dump, internal assessment or proprietary detailed inventory is committed.

## Reconstruction limits

The prior conversation’s assistant responses were unavailable as readable text. Its user messages and attachments established the principal structure. Catalogue IDs, page hierarchy, starter definitions, lifecycle states, industry selections and intake implementation are implementation decisions, not a claim to reproduce an unavailable final blueprint word for word.

## Canonical records

`catalogue/areas.json` defines architecture areas. `catalogue/capabilities.json` defines capabilities. `catalogue/resources/*.json` defines external resources. Generated catalogue pages must be rebuilt after records change. Each capability has one owner area; other views link to it. A resource can reference several capabilities and appears only once in the canonical store.

## Content maturity

Planned: scope and intended deliverable only. In progress: useful framing with unfinished depth. Curated: a resource has been reviewed for relevance and public use. Retired: retained metadata explains why it is no longer recommended. Maturity is not an assurance rating.

Capability detail pages expand the canonical definition. Validation checks that each page retains its canonical name, definition and acceptance example; update those fields together when refining a capability.
